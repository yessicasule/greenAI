## 3. How energy numbers are verified

**Instrument.** NVML `nvmlDeviceGetTotalEnergyConsumption` — the GPU's
on-board cumulative energy counter (mJ resolution, supported on the T4).
This is a hardware measurement, not a software estimate. If a node lacks
the counter, the script falls back to integrating 20 Hz power samples and
the validator flags the run with a WARN that must be disclosed.

**Protocol.** Greedy decoding (deterministic), fixed `max_new_tokens=128`,
5 warmup generations before measuring, one tier in GPU memory at a time,
`torch.cuda.synchronize()` around timings, actual generated-token counts,
idle-power baseline and GPU/driver identity recorded in
`hardware_info.json`. Full sweep repeated 3× (different days/nodes);
reported as mean ± 95% CI.

**Derivation rule (Session 4).** Because greedy decoding is deterministic,
a router's per-prompt response and energy equal those of the tier it picks.
Phase A measures every prompt on every tier; every routing condition is then
an exact function of measured data — nothing is modeled. Router compute
overhead is measured separately and reported (it runs on CPU in
milliseconds; claiming it as zero would be wrong, so it is quantified).

**Automated gate.** `scripts/verify_results.py` checks every results file
for: non-emptiness, minimum n per tier (≥30), positive energies and token
counts, J/token inside a physical plausibility window for a 1B model on a
T4 (0.05–50 J/token), CI tightness, ≥3 repeated runs, complete
prompt×tier measurement grids, and internal consistency (oracle must be the
accuracy maximum; a 4-bit-costs-more-than-fp16 result triggers the §5 risk
warning). **Policy: a number appears in the paper only if its checks PASS;
WARNs must be acknowledged in the paper's threats-to-validity section.**

## 4. How accuracy numbers are verified

- **Benchmark accuracy** comes from lm-eval-harness (community-standard,
  versioned tasks), seeds fixed at 42, tiny-Benchmarks tasks or standard
  tasks with a documented example limit. Raw JSON output is kept.
- **Routed-set correctness** uses a reference-match proxy (numeric match for
  math, normalized substring for short facts, token-F1 ≥ 0.5 otherwise).
  This is a *proxy* and is labeled as such everywhere; the paper's
  benchmark-accuracy claims come only from lm-eval.
- Sanity cross-checks: accuracy ∈ [0,1]; fp16 not beaten by 4-bit beyond
  noise (else the eval setup is investigated before anything is reported).

## 5. Known threats to validity (to be reproduced in the paper)

1. **Hardware scope.** All measurements are on one GPU class (T4). Findings
   may differ on A100/H100 or CPUs. Claims will be scoped to "commodity
   inference GPUs of the T4 class."
2. **Quantization kernel reality.** bitsandbytes dequantizes to fp16 for
   compute; low-bit tiers may not save energy proportionally to bit-width —
   this is measured, not assumed, and the outcome is reported either way.
3. **Model scope.** One model (Llama-3.2-1B). No claim is made about other
   sizes/families without measurement.
4. **Correctness proxy.** Reference-match correctness on the routed set is
   an approximation (§4); oracle conditions inherit its noise.
5. **Shared-infrastructure noise.** Kaggle nodes vary in thermals/hosts;
   mitigated by 3 repeat runs on different days and CI reporting, and
   disclosed regardless.
6. **Energy counter scope.** NVML measures GPU-board energy only; CPU/DRAM
   host energy is excluded and stated as such.
